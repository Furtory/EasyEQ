# 自动风味：评估与设计

日期：2026-10-29
状态：评估完成，未实施

## 一句话结论

自动风味不做"生成一条新曲线"，只做一件事：**根据正在播放的声音，算出九条风味各自的增益**，然后交给现有的叠加层管线。
它属于"参考匹配"这一类智能 EQ——听一段长时平均谱，和选定的目标比，差多少补多少。

不做曲目识别、不联网、不训练模型、不做逐帧动态 EQ。

---

## 1. 要解决什么

现状（S14）：风味是九条固定滤波器（爆炸 / 余震 / 男声 / 女声 / 脚步 / 枪声 / 齿音 / 空间 / 尖啸），
用户靠拖手柄和滚轮自己调。会调的人能调得很快，不会调的人不知道往哪拖。

自动风味要回答的问题不是"这是什么"，而是——**"这段声音现在缺什么、多什么，按我要的方向该怎么补"**。

这个区别决定了后面所有设计：既然只需要"缺什么"，就不需要分类器、不需要指纹、不需要知道曲名。

## 2. 其他智能 EQ 的五类做法

### 2.1 参考匹配（音调平衡）

| 产品 | 做法 | 用户要给的 |
|---|---|---|
| [sonible smart:EQ 4](https://www.sonible.com/smarteq4/) | smart:filter 把信号"配平"到选定 Profile 的频谱形状；Profile 含乐器、人声、整轨、**按流派的目标**，还能加载**参考曲**生成自定义目标；可限定**最长学习时间**；可拆权重曲线**指定只在哪段频率动手**；Smoothing / Adaptive 两个参数 | 选 Profile、学习窗口、平滑度、自适应、作用频段 |
| iZotope Tonal Balance Control | 把混音的长时频谱与流派目标区间对比，超界提示 | 选流派 |
| AutoEq / 哈曼 | 耳机频响 → 目标曲线 → 参数 EQ | 选目标 |

原理：取一段音频的长期平均谱（LTAS），减目标谱，差值就是 EQ 曲线。

一个容易漏掉的信号：smart:EQ 4 的官网上写着「应需求增加了最长学习时间」。
连专业工具自己也发现，学习窗口越长、结果越不跟手，所以宁可限时——这条正好替我们背书：不该靠"采得久"来稳，而该靠"存得全 + 事后能翻"。

好处：可解释、可离线、结果稳定、参数少。
坏处：目标选错会越修越怪；平均谱会被最响的片段带偏；素材本来就好时会做无谓修正。

**这是我们的主路线。** 仓库里已经有：回环采集、频谱数学、`EqResponse` 频响仿真、九条风味。缺的只是一张目标表和一个 LTAS 累加器。

### 2.2 感知自适应（听觉模型）

**Soundtheory Gullfoss** 是最典型的（参数与机制见 [SOS 评测](https://www.soundonsound.com/reviews/soundtheory-gullfoss)）：基于人耳掩蔽/听觉感知模型，实时算出一条持续变化的曲线——
把快被其他声音盖住的抬起来（Recover）、把过度占位的压下去（Tame），拿不准时用 Bias 决定偏哪边；
Brighten 调整体明暗，Boost 按等响曲线随电平补低频；两个频率标记限定作用区间；输出电平自动匹配输入。
**全部参数只有五个。**

原理：不分类内容，逐帧判断"哪里被挡住、哪里过冲"。

好处：效果最好，参数最少。
坏处：需要掩蔽模型和精度很高的动态 EQ，做不好会让声音变薄、把枪声的脆度削掉；没有"正确值"，全凭耳朵。

**我们做不精，只借它的思想**：少参数、结果连续、按强度缩放。

### 2.3 响度补偿

Audyssey Dynamic EQ、Dolby Volume、Gullfoss 的 Boost 都属于这一类：按**音量**补低频和高频（等响曲线），
小音量时人耳对低频不敏感，所以补回来。它和"内容是什么"完全无关。

**不混进自动风味。** 真要做，是独立的"音量联动"开关。

### 2.4 测量校正

Dirac Live、Sonarworks、Audyssey，以及本项目的自动EQ：播扫频、麦克风测、按目标拟合。
修的是"设备 + 房间/耳机"，不是"这段内容"。

和自动风味的关系：一个修设备，一个修内容，可以串，不能互相替代。自动EQ 测完再开自动风味，是合理的组合。

### 2.5 元数据 / 进程

游戏套件按进程切预设；本项目的"自动切换"已经绑定前台进程。便宜、可靠、零延迟，但只能回答"在玩什么"，
回答不了"这段声音缺什么"。**本方案不需要它**——方向由用户选，不做分类。

### 2.6 对照

| 类别 | 输入 | 更新 | 用户给 | 我们 |
|---|---|---|---|---|
| 参考匹配 | 长时平均谱 | 每次 8–20 s | 方向 | **做** |
| 感知自适应 | 逐帧谱 + 掩蔽模型 | 毫秒 | 5 个比例 | 只借思想 |
| 响度补偿 | 音量 | 随音量 | 无 | 不做 |
| 测量校正 | 扫频 + 麦克风 | 一次 | 目标曲线 | 已有 |
| 元数据/进程 | 进程名 | 事件 | 绑定 | 不需要 |

一句话区别：**参考匹配修"这段内容偏了什么"，感知自适应修"此刻什么被挡住"，测量校正修"设备偏了什么"。**

## 3. 为什么落在"九条风味"上

试过的另一种设计是"自动生成整条 EQ 曲线、替换左右层"。放弃的理由是结构：

| 需求 | 替换整条曲线 | 只算九条风味 |
|---|---|---|
| 不破坏预设 | 会写进 `.peace`，和用户曲线混在一起 | 风味本来就不进 `.peace` |
| 可撤回 | 要单独做一套历史 | 复用 `EqDraft`，应用即一步撤回 |
| 可对比 | 只能整条 A/B | 九条可以单独听、单独改 |
| 和手动共存 | 冲突 | 应用后用户照样拖手柄 |

而且九条风味本来就是"听得出来但说不出位置"的分类，正好是输出的天然维度。

## 4. 用户期望：八个方向

改成「一个游戏向 + 七个内容向」，名字按黑钨定的来：竞技定位是唯一的战术射击入口，
其余是流行通用 / 摇滚金属 / 女声电子 / 男声民谣 / 人声增强 / 爵士蓝调 / 古典舒缓。

目标形状（相对 1 kHz，dB），顺序固定为
爆炸 / 余震 / 男声 / 女声 / 脚步 / 枪声 / 齿音 / 空间 / 尖啸：

> 这张表是早期的手调初值，代码已经不用它了。现在每格目标都由公开配方换算，
> 逐条数值与出处见 [自动风味-目标表来源.md](自动风味-目标表来源.md)。
> 保留在这里只当设计意图的记录，别照着它改代码。

| 方向 | 适合 | 目标形状 |
|---|---|---|
| **竞技定位** | FPS、战术射击 | −7 / −5 / 0 / 0 / +7 / +4 / −2 / +1 / −2 |
| **流行通用** | 华语流行、榜单歌 | +1 / 0 / +2 / +2 / +1 / +1 / −2 / +1 / −1 |
| **摇滚金属** | 摇滚、金属、朋克 | +3 / +2 / +1 / +2 / +3 / +3 / −2 / 0 / −2 |
| **女声电子** | 女声、电音、ACG | +5 / +3 / +1 / +3 / +1 / +1 / −1 / +3 / 0 |
| **男声民谣** | 男声、民谣、木吉他 | −2 / −1 / +4 / −1 / +1 / 0 / −2 / +1 / −2 |
| **人声增强** | 播客、会议、解说 | −5 / −4 / +4 / +3 / 0 / −1 / −2 / −3 / −3 |
| **爵士蓝调** | 爵士、蓝调、现场 | +2 / +1 / +2 / +1 / +1 / −1 / −3 / +1 / −2 |
| **古典舒缓** | 古典、器乐、管弦 | +1 / +1 / +1 / +1 / 0 / 0 / −2 / +2 / −2 |

每个方向另带硬约束：

- 竞技：爆炸只削不抬，余震只削不抬，尖啸只削不抬，空间最多 +2（抬了就糊脚步）。
- 流行通用 / 摇滚金属 / 女声电子：齿音只削不抬，尖啸最多 +2；摇滚把空间压到 +2 以内，免得镲片糊。
- 男声民谣：只抬男声那条，女声上限 +2；低频只小削，不砍干净。
  （实现已经改成按配方算：男声中心只有 +0.33 dB，靠的是 2–4 kHz 的清晰度，不是 700 Hz 的厚度；
  方向表另带人声标识 `VoiceBias`，男声偏低、女声偏高，供后续「有没有测到人声」的判断使用。）
- 人声增强：男声女声一起抬，低频砍到 −6 上限，齿音只削。
- 爵士蓝调：齿音 −3 封顶（再削会闷），尖啸最多 +2。
- 古典舒缓：整体贴着 0 dB，只压齿音和尖啸、放一点空间。
- 所有方向：齿音永不为正。

这八个数是待调的初值，不是测量真值。它们表达"这个方向希望内容长成什么样"，
实际增益由实测与它的差算出来，再乘强度。

**强度 0–100%**：整条建议乘一个系数，默认 60%。它同时决定「剔掉多少不可信数据」（见 6.6）——
判错时把它拉小，既减弱效果，也少做取舍，是唯一需要「手感」的旋钮。

## 5. 界面

### 5.1 控件

模式外，这一排是：

```
风味 [下拉] [应用到其他配置] [自动风味]
```

点「自动风味」后，手动那排全部隐藏，换成六个：

| # | 控件 | 出现时机 |
|---|---|---|
| 1 | 期望方向（4 项） | 进模式即有 |
| 2 | 强度（0–100%，默认 60%）：同时定味道浓度和抗干扰力度 | 进模式即有 |
| 3 | 开始录制 → 倒数 → 暂停录制 / 继续录制（同一按钮换字） | 进模式即有 |
| 4 | 对比 | 暂停且有数据时 |
| 5 | 应用 | 暂停且有数据时 |
| 6 | 取消 | 进模式即有 |

模式内右下角「撤回 / 还原 / 保存 / 取消」整组收起，退出时恢复——否则两个"取消"打架。
宽度约 570 px，比现在这排还窄，最小窗口宽度不会被迫变化。

对照业界：smart:EQ 4 是 Profile / Smoothing / Adaptive / 作用频段 4 个，Gullfoss 是 5 个 + 两个频率标记。
**常驻 4–6 个是这类功能的正常量级**，再多就变成要读说明书的工程软件。

### 5.2 状态机：听、看、草稿三份分开

| 状态 | 按钮 | 听到的风味 | 图上的风味 | 数据 |
|---|---|---|---|---|
| O 模式外 | — | 当前风味 | 当前风味 | 无 |
| A 已进入，没录过 | 开始录制 | 当前风味 | 当前风味 | 空 |
| B 倒数 5→1 | 倒计时数字 | **全 0（校准链）** | 全 0 | 空 |
| C 录制中 | 暂停录制 | **全 0（校准链）** | **实时建议** | 每 100 ms +1 帧 |
| D 暂停，有数据 | 继续录制 | 建议（对比态下是全 0） | 建议 | 冻结，不丢 |
| E 应用后 | — | 建议 | 建议 | 清空，退出模式 |

**校准链** = 左右层 + 低音层（仅当「叠加低音修正」打开）+ 风味全 0。

听和看分开，是这套设计的关键：录制时声音里没有风味，分析就不会被自己的结果污染；
因为不叠加，拖滑杆只改图、不改声，所以录制中允许随时调，不会形成正反馈。

暂停不是结束：数据一直在，按钮变成「继续录制」，接着累加。
只有取消或应用才清空——这样录制中途去调一下、再回来接着录，前面那段不会白费。

### 5.3 操作规则

1. 点「自动风味」：手动控件隐藏，露出方向 / 强度 / 开始录制 / 取消。
2. 点「开始录制」：**先把声音切成校准链**（风味归 0，低音按叠加开关），写一次 `peace.txt`；
   然后倒数 5→4→3→2→1，每秒一次；归 0 停 1 秒进入录制，按钮变「暂停录制」。
3. 录制：不设时长上限，每 100 ms 存一帧。有效帧不足 30 时图上不画，也不出建议。
   整个录制期间声音都是校准链。
4. 录制中拖方向或强度：只重算图形，不动声音——声音本来就是校准链，所以随时可调。
5. 点「暂停录制」：停止累积，按钮变「继续录制」，对比 / 应用 / 取消出现；数据一帧都不丢。
6. 点「继续录制」：立刻接着录，**没有倒数**（人已经在机房/游戏里了）；数据在原基础上累加，
   曲线在接缝处只是继续长，不重新开始。
7. 对比（只在暂停时）：一次点→全 0（听到的就是校准链），再点→建议，可反复。**不进撤回、不置脏、不动草稿。**
8. 应用（只在暂停时）：提交进草稿，+1 步撤回，退出模式；数据清空。
   **点保存才写 `.peace` 和 `ui-state.json`。**
9. 取消（随时）：退出模式，声音回进入前，**数据清空**；不动撤回，也不动进入前那些未保存的改动。
10. 调强度：录制、暂停都能拖。它同时改味道浓度和抗干扰力度，曲线当场重画；
    暂停时如果正在对比（全 0），拖强度只更新建议，不打断归零状态。

### 5.4 守卫

| 情况 | 处理 |
|---|---|
| 不在「左右」编辑态 / 在「低音」编辑态 | 入口不出现（风味本来就只属于左右层） |
| 自动EQ 测量中、试听扫频中 | 入口禁用（它们会临时改写 `peace.txt`） |
| 模式中改「叠加低音修正」 | 冻结该开关（录制和暂停都冻），保证反解用的链路始终一致 |
| 模式中改两层曲线 | 禁止（手柄不可拖、空白处不能建点），保证反解用的那份点列表不变 |
| 录制中或暂停中取消 | 停表、清数据、声音回进入前，退出模式 |
| 抓不到输出 / 整段静音 | 不出建议，状态栏说明，保持「暂停」等用户再录 |
| 模式中退出编辑 / 切预设 / 关窗 | 先撤预览、退出模式，再执行原操作 |
| 对比 = 0 时点应用 | 先回建议、再提交 |
| 录制中按 Ctrl+Z | 不响应 |

没有浮层，所以也没有「剔太多」「浮层收起」这类需要兜底的状态。

## 6. 算法

### 6.1 采样与存储

复用常开的回环采集（右侧电平表本来就靠它），不新开 WASAPI 客户端。

新增 `LtasRecorder`：环缓冲最近 8192 个单声道样本；录制期间每 100 ms 取一帧；
峰值低于 −45 dBFS 的帧直接丢；否则做一次 FFT，按 **1/12 倍频程**（20 Hz–20 kHz，120 条）积分功率，
把这一帧存下来：120 个 dB 值 + 峰值 + 时间戳。

为什么不还是九条：九条只够算增益。要算 Q 和中心频率，得看见每条风味「自己那一段」的形状——
峰落在哪、半高宽多少。1/12 倍频程（约 6% 带宽）刚好能分辨到 Q ≈ 10；再细只是浪费。

一帧 120×4 + 4 + 4 = 488 字节，10 Hz 下约 4.9 KB/s：

| 采样时长 | 帧数 | 内存 |
|---|---|---|
| 10 分钟 | 6,000 | 2.9 MB |
| 1 小时 | 36,000 | 17.6 MB |
| 30 小时 | 1,080,000 | 527 MB |

存的是频谱包络，不是波形。同样 1 GB，存 48 kHz 立体声裸波形只够 1.5 小时，存包络能放五十多个小时。

上限取两个条件的较小值：**1 GB** 与 **系统可用内存 − 2 GB**。到线就停止采样、用已有数据出结果，
状态栏写明「内存到顶，已自动停止录制」——不静默丢帧，也不让界面卡死。
缓冲按 4 MB 分块预分配，避免大对象堆碎片。

不写盘：这是「你听了什么」的频谱指纹，没有留在磁盘上的理由。退出自动风味时整块释放。

### 6.2 为什么不直接用现成的频谱帧

`SpectrumAnalyzer.Snapshot()` 带"快升慢落、每帧最多回落 3 dB"的显示平滑。
它每秒被调用 60 次，把那些帧平均起来，瞬态会被系统性抬高——游戏音效恰恰是最多瞬态的内容。
所以累加器必须自己做 FFT，不能抄近路。

### 6.3 反解

录制期间写进 `peace.txt` 的就是「左右 + 低音」的合并点列表，所以直接拿它求增益：

```csharp
// 现成 API，直接吃 EqPointList
eqGain[i] = EqResponse.OthersGainAt(mergedPoints, 中心频率[i]);
```

这一步是防"自己测自己"的：回环已实测抓到的是**已过 EqualizerAPO** 的声音，
不扣掉两层曲线，就会把用户自己调过的 EQ 当成"内容本来就这样"，然后重复补一遍。

### 6.4 估计函数（一个纯函数）

关键变化：估计不再是「边采边累加」的状态，而是 `Estimate(frames, 参数)`。
同一批数据、不同参数，可以反复算——录制中算、暂停后算、拖滑杆再算，都是同一个函数。

```
Estimate(frames, p) → 九条 (频率, 增益, Q)
p = { 时间范围, 剔除比例, 安静百分位 }

A. 先挑帧
① 按时间范围裁剪
② 丢掉峰值 ≥ −0.5 dBFS 的帧（削波，本身已经失真）
③ 丢掉太安静的帧：响度低于「本段第 Q 百分位」的整帧不要（Q 由强度给，见 6.6）
④ 逐带找瞬态（不是整帧）：某条带比自己的中位高出 12 dB、持续不到 T(f) 的，
   这一段在这条带上判为爆音——只丢这条带的值，不丢整帧，低频的轰鸣没理由污染 8 kHz。
   T(f) = base(强度) × (1000/f)^0.4，夹在 80–500 ms（低频允许更长，见 6.6）
⑤ 反复出现的不算爆音：形状相近、出现 ≥ 3 次的事件当内容留着——
   枪声再短促也会连发，真正的偶发爆音只出现一次
⑥ 每帧：source(f) = bandDb(f) − eqGain(f)；shape(f) = source(f) − 中频三点均值
⑦ 逐带取中位数 → 中位谱（只用来定位，不当结果）
⑧ 第一遍：每条带按 |值 − 本条中位数| 排序，丢掉最远的 base 个 → 粗 shape(f)
⑨ 用粗 shape 算 Δ(f) = target(f) − shape(f)，得到「这条带有多需要改」：
   w_b = |Δ_b| / max|Δ|，夹在 0–1
⑩ 第二遍：每条带重剔，X_b = base × (1.6 − 0.8·w_b)，再对剩下的取均值 → 最终 shape(f)
   需要改得多的带少剔（多留数据、估得更稳），不需要改的带多剔（错了也没人听得出）

B. 再拟合九条
⑪ 每条有「责任区间」：上一个中心的中点到下一个中心的中点，再夹进它的 Covers 范围
⑫ 区间内 Δ(f) = target(f) − shape(f)，找峰值位置 → 频率
⑬ 峰值上下各降 3 dB 的两点 → 带宽；Q = 中心频率 / 带宽
⑭ 增益 = 峰值，夹取后 × 强度
⑮ 峰 < 1.5 dB、或半高宽量不出来 → 频率、Q 保持默认，增益 0
```

逐带剔除而不是整帧，理由和瞬态一样：某条带在某一帧突然跳起来，不该连累其它带。
代价是拼出来的形状可能不对应任何一帧真实的频谱——这和「中位数只用来定位」是同一个取舍，
我们估的是「典型形状」，不是「某一帧」。

**安静剔除留在帧级，不逐带。** 这一条我保留，理由很硬：
如果逐带丢「本条最安静的 14%」，安静带被抬高的幅度大、热闹带小，形状会系统性变形，正是最怕的那种偏差。
「有没有声音」本来就是整段的事，不是某一条带的事。你要的「重点带少剔、非重点带多剔」，
由逐带离群剔除拿到，不需要动安静剔除。

两遍的代价是 O(2N·B)：几千帧 × 120 带，重算一次仍是毫秒级。

责任区间是必须有的：相邻风味的覆盖范围重叠（脚步 1.5–4 kHz、枪声 2–7 kHz），
各拟合各的会把同一段缺陷算两遍，叠出来是个坑。按中点分工，每条只管自己那一段，边界上 Δ 仍然连续。

`target(f)` 由四个方向的八点表在对数频率上插值得到，所以任何频点都有目标值。

Q 的夹取：中间六条 0.5–4，两条架式 0.5–1.2；频率夹进各自的 Covers。
这不是保守——这类内容本来就宽，拟合出 Q 12 的窄坑，多半是把某个音效的共振当成了整体缺陷。

为什么是「中位数定位 + 剔除 + 均值出结果」，而不是直接平均：
爆音和零星枪声在频谱上离群，均值会被它们拽走；中位数先把「典型形状」钉住，
再按距离砍掉尾巴，剩下的均值才稳。

也不拿逐带中位数直接当结果——120 个中位数拼起来可能不是任何一帧真实存在的形状，高低频会打架。

这条路线和 smart:EQ 的差别：

| | smart:EQ | 本方案 |
|---|---|---|
| 频率轴 | Smoothing | 相邻带 0.5 / 0.3 / 0.2 平滑 |
| 时间轴 | Adaptive：对高动态素材把曲线稳住 | 事件过滤 + 中位定位 + 逐带按距离剔除 |
| 窗口 | 可设最长学习时间，到点冻结 | 全量保留，事后按时间范围 / 事件重算 |
| 输出 | 一条滤波曲线 | 九条的频率、增益、Q 全给，应用后还能手改 |

它限时是为了「别跟太久」，我们全留是为了「可以往回翻」——用户能自己删掉一段，比程序猜哪段该丢更可靠。

### 6.5 实时显示

录制中每 500 ms 用同一个 `Estimate` 对「目前已收到的帧」重算一次（几千帧 × 120 带，仍是毫秒以内），
把结果作为"图上的风味"通知给曲线控件：

- 录制中：九条曲线用虚线 / 60% 不透明，无手柄。
- 暂停后：恢复实线、出手柄（仍不可拖）。
- 有效帧不足 10 个：不画。

实时和最终走的是同一个函数、同一批数据，所以按停止的那一刻曲线不会跳——它只是不再变。

### 6.6 强度就是全部取舍

只有一条滑杆，没有第二层设置。它同时定三件事：

| 强度 | 味道浓度（增益系数） | 剔除离群 | 忽略最安静的声音 |
|---|---|---|---|
| 0% | 0.0 | 2% | 0% |
| 60%（默认） | 0.6 | 约 8% | 约 14% |
| 100% | 1.0 | 20% | 40% |

三件事里有两条本来就是占比，跟 dB 无关：

- 剔除离群：按与中位谱的偏离程度丢掉最远的那部分帧。
- 忽略最安静的声音：不是「低于 −45 dBFS 不算」，而是「响度最低的 14% 不算」。百分位按这段声音自己算，
  所以游戏音量开大关小、换耳机、换声卡，都不用重调——这比固定 dB 门限稳。
- 时间范围：不做成参数，固定成「自动裁掉首尾的静音段」。

映射用平方曲线（2 + 18s²、40s²），不用直线：低强度区间几乎不动，高强度才明显收紧。
默认 60% 正好落在剔除 8% 附近。

滑杆给的是 base，每条带真正剔多少还要乘一个「这条带要不要改」：

| | 不需要改的带（w=0） | 要改的带（w=1） |
|---|---|---|
| 强度 0% | 3.2% | 1.6% |
| 强度 60% | 约 12.8% | 约 6.4% |
| 强度 100% | 32% → 夹到 30% | 16% |

为什么同向合理：强度低＝改动小，零星爆音本来也带不偏多少；强度高＝改动大，才更需要把不可信的数据扔掉。
越用力越挑食，这两件事不矛盾。反过来，让「想要更带感」变成「剔除更少」，那才是真矛盾。

还有一条规则不单独占控件：高出中位 12 dB 的瞬态，只在「持续不到 T(f)」时才判爆音。T(f) 按频率分档：

| 频带 | 0% | 60% | 100% |
|---|---|---|---|
| 80 Hz（爆炸） | 330 ms | 500 ms | 500 ms |
| 700 Hz（男声） | 140 ms | 280 ms | 370 ms |
| 2.5 kHz（脚步） | 80 ms | 165 ms | 220 ms |
| 7 kHz（齿音） | 80 ms | 110 ms | 145 ms |
| 12 kHz（空间） | 80 ms | 90 ms | 120 ms |

低频阈值放宽不是妥协，是让判据和分辨率对齐：一个 80 Hz 的周期就是 12.5 ms，加上房间/耳机的余响，
低频瞬态本来就长；8192 点 FFT 的时间窗是 171 ms，低频在时间轴上被抹得更开。
拿 200 ms 一刀切，低频要么全被当成爆音，要么一个都抓不到。

**枪声短促，所以只靠时长必然误判。** 第二条判据是次数：把形状相近的瞬态聚成类，
出现 ≥ 3 次的当内容保留——连发、点射、换弹都会重复，真正的偶发爆音只吭一声。
这条是固定的，不跟滑杆走。

帧是 100 ms，所以时长按 100 ms 一档算；50 ms 的爆音记成 100 ms。

**代价要说清楚**：没有浮层，就没有「单独跳过某一段、单独恢复某个瞬态」的入口。
规则误判时（比如把一段连续枪声当爆音），用户只能降强度，或者取消重录。
这是拿「少一个界面」换的：多一个浮层，等于多一套要解释的参数，而小白用户不会去开它。
真要补，最自然的位置是曲线上的一个小提示（「已忽略 3 段瞬态」，点开才展开时间轴），不进这一版。

### 6.7 参数

| 参数 | 值 | 理由 |
|---|---|---|
| 倒数 | 5 s | 给切窗口/开一局的时间 |
| 采样时长 | 不设上限 | 点「暂停录制」即停；游戏声音本来就断续 |
| 出结果门槛 | 有效帧 ≥ 30 | 按「听到的声音」计数，不按墙钟 |
| 取帧 | 100 ms | 每秒 10 帧；事件时长分辨率 100 ms |
| 存储 | 488 B/帧 | 120 带 × 4 B + 峰值 + 时间戳；1 小时约 17.6 MB |
| 内存上限 | min(1 GB, 可用 − 2 GB) | 到线自动停止，用已有数据出结果 |
| 瞬态规则 | 高出中位 12 dB、短于 T(f)（80 Hz 最长 500 ms，高频 80–120 ms） | 按频率分档，避免低频误判 |
| 重复判定 | 形状相近出现 ≥ 3 次当内容 | 枪声短促但会连发，不靠时长区分 |
| 剔除离群 | base 2–20%（随强度），逐带再乘 0.8–1.6 | 要改的带少剔、不改的多剔 |
| 安静百分位 | 0–40%，随强度走（默认约 14%） | 相对本段算，换设备不用重调 |
| 削波门 | −0.5 dBFS | 已经失真的帧不要 |
| Q 范围 | 中间六条 0.5–4；架式 0.5–1.2 | 内容本来就宽 |
| 频率夹取 | 各自的 Covers | 和手动拖动同一套限制 |
| 死区 | 峰值 < 1.5 dB 不动 | 听不出来的改动不做 |
| 提升上限 | 低频 +6 / 齿音 +3 / 其余 +9 | 护住底噪和失真 |
| 衰减上限 | −12 dB | 和自动EQ 的夹取一致 |
| 强度默认 | 60% | 第一次用不该是最激进的 |
| 画面重算 | 500 ms | 看着跟手，又不抖 |

### 6.8 人声检测与补偿

男声民谣 / 女声电子这两条方向，在「预设目标」之上再对人声频段叠一点补偿。
补不补、补多少，由「这段录音里有没有人声」决定；其余六个方向完全不参与。

**没有用「人声/伴奏分离」模型。** 评估过的方案与结论：

| 方案 | 许可 | 体积 / 运行时 | 实时性 | 结论 |
|---|---|---|---|---|
| Silero VAD | MIT | 模型 2.3 MB，ONNX，纯 CPU | 32 ms 窗不到 1 ms | 采用 |
| Demucs（htdemucs） | MIT | 80 MB+，要 PyTorch | CPU 约 10–40 倍实时 | 不用 |
| Spleeter | MIT | 50 MB+，要 TensorFlow | 慢、音质差、已停更 | 不用 |
| UVR5 / MDX-Net | GPL / 权重许可不一 | 数百 MB，桌面 GUI | 慢 | 不用 |

不用的三条硬理由：发布包会从几十 MB 涨到数百 MB；一次可录 20 分钟，分离在 CPU 上要等半小时以上；
我们的分析对象本来就是长时平均谱，人声帧的子集已经能代表「人声频段长什么样」，不需要真的把伴奏剥掉。

**数据流**：WASAPI 单声道 → 每 100 ms 取最近一段 → 降到 16 kHz → Silero 按 32 ms 窗判语音 →
任一窗命中就把这一帧标成「有人声」→ 帧标签跟 120 带频谱存在一起。

**补偿规则**（常量在 `AutoFlavorAnalyzer`）：

```
ratio      = 有效帧里人声帧占比
confidence = ratio < 5% ? 0 : clamp(ratio / 30%, 0, 1)
boost      = 2.5 dB × confidence
target     = 预设目标 + boost × 权重（主带覆盖范围内为 1，往外一个倍频程线性归零）
```

主带由 `AutoFlavorVoiceBias` 决定：男声方向加权在 300–1200 Hz（男声条），
女声方向加权在 1000–3500 Hz（女声条）。补偿叠在目标上，再照常和实测比，
所以上下限、死区、瞬态剔除全部沿用，没有第二套规则。

**失败降级**：模型没打进包、ONNX 加载失败、推理抛异常，都退回「没有人声标记」，
结果与加这个功能之前逐位相同；状态栏会写明不可用，不弹窗、不阻断录制。

**实测（2026-10-30）**：模型 2 327 524 字节。输入不是 512，是 **576**：
官方 `OnnxWrapper` 把「上一窗尾巴 64（context_size）+ 这一窗 512」拼起来再喂，
直接喂 512 不会报错，但输出恒在 0 附近。state 是 `(2,1,128)`，每次用返回的 `stateN` 覆盖。

分素材实测（16 kHz 单声道，逐 512 窗）：

| 素材 | 最高概率 | 过 0.5 的窗 |
|---|---|---|
| 纯语音（系统 TTS 8.2 s） | 1.000 | 190/255 |
| 纯音乐（三和弦） | 0.021 | 0 |
| 语音 + 音乐，人声 0 dB | 0.187 | 0 |
| 语音 + 音乐，人声 −3 dB | 0.051 | 0 |
| 语音 + 音乐，人声 −6 dB | 0.040 | 0 |

**结论：Silero 只认接近纯语音的输入。** 人声一旦和伴奏同响，概率掉到 0.2 以下，
和纯音乐的 0.02 之间没有安全的可分区间。所以这个功能对「歌曲」无效，
只适用于游戏语音、解说、播客这类干净人声；歌曲里的人声要靠分离模型，
而分离模型（MDX-Net 等，30–60 MB）在当前网络下拿不到。

另试过不依赖模型的频谱启发式（2–8 Hz 包络调制占比）：
纯音乐 0.90、纯语音 0.16、混音 0.04–0.23，三者不可分，放弃。

**2026-10-30 调整：补偿不再依赖检测。** 既然检测在歌曲上不可靠，拿它当开关会让
「听歌选人声方向」直接失效。现在的规则是：

- 男声/女声方向一律固定补 2.5 dB（`AutoFlavorAnalyzer.VoiceBoostDb`），不看检测结果
- 检测占比只显示在曲线图那条提示里，不参与增益
- Silero 本身保留，用途转到自动切换页的「语音唤醒」：检测到人声就套用绑定的那组配置

## 7. 关键风险：回环抓到的声音过没过 EQ

整套算法都建立在"能算出内容本来的样子"上。如果回环抓到的是已经过 EqualizerAPO 的声音，
而程序又不做反解，就会形成正反馈：抬低频 → 测到更多低频 → 继续抬。

### 7.1 本机已核实的事实（只读检查，2026-10-29）

| 检查项 | 结果 |
|---|---|
| EqualizerAPO 安装 | `C:\Program Files\EqualizerAPO`（含 `EqualizerAPO.dll`） |
| 配置文件 | `config.txt` 里有 `Include: protect.txt`、`Include: peace.txt` |
| 端点上的 APO 注册 | 只有 **`Music`**（状态 = active）挂了两条 EqualizerAPO CLSID：`{EACD2258-FCAC-4FF4-B36D-419E924A6D79}`、`{EC1CC9CE-FAED-4822-828A-82A81A6F018F}`；`DAW`、`Voice` 等其它活动端点都没有 |
| 回环实验（2026-10-29 实测） | 「爆炸」+12 dB 时 80 Hz 频谱同步抬起，归零同步回落 —— **post-EQ 已确认** |

### 7.2 结论

APO 由音频引擎在把数据交给端点之前处理，WASAPI 回环读的正是端点这一侧的数据，所以抓到的是已过 EQ 的声音。
2026-10-29 的实测印证了这一点：把一条风味抬到 +12 dB，频谱对应频段同步抬起，归零同步回落。

所以 §6.4 里扣掉两层响应的那一步必做，不能省。`Music` 这个名字像虚拟声卡（Voicemeeter 那几个虚拟输入），
实测说明虚拟设备上的顺序也一样。

### 7.3 P0 实验（三步，不用写代码，不用装东西）

1. 打开这个程序，进「左右」编辑态，确认底部曲线下方开着「频谱显示」。
2. 放一段有低频的音乐（或游戏里持续有爆炸/引擎声的场景），把「爆炸」这条风味拖到 **+12 dB**。
3. 看曲线底部那条频谱：**80 Hz 附近是否明显抬起来**。

实测结果落在第一行。判定表留作复测参考（换设备、换版本时重跑）：

| 现象 | 结论 | 代码分支 |
|---|---|---|
| 频谱跟着抬起、归零也跟着落 | post-EQ | 保留 §6.4 ①②，`LoopbackIncludesApo = true` |
| 频谱纹丝不动 | pre-EQ | 跳过 ①②，`LoopbackIncludesApo = false` |
| 抬一点但明显不足 | 部分处理 | 先按 post-EQ 做，实测差值写进补偿表 |

这一步已经做完（2026-10-29），结论见 7.1 第四行。换设备、换 EqualizerAPO 版本时按这张表复测。

## 8. 失败模式

| 失败 | 表现 | 兜底 |
|---|---|---|
| 回环是 post-EQ 且未反解 | 越调越闷 | §6.3；P0 定案 |
| 录制里混进自己的建议 | 循环强化 | 录制期间声音里没有风味（校准链） |
| 平均谱被最响片段带偏 | 建议偏亮或偏闷 | 中位定位 + 事件过滤 + 逐带按距离剔除 |
| 用户先听到不想听的变化 | 以为软件乱改 | 结果出来才出声；对比一键归零；强度可调 |
| 整段静音 | 建议乱飞 | 有效帧 < 30 不出结果 |
| 采样把内存吃满 | 系统变卡 | 到 1 GB 或可用 < 2 GB 自动停止，用已有数据出结果 |
| 短促枪声被当爆音 | 建议缺一块 | 逐带判、且重复 ≥ 3 次就保留；再不行降强度或取消重录 |
| 强度拉满削波 | 峰值顶到 0 dBFS | 提升上限 + 现有预增益逻辑 |
| 误点应用 | 声音变了 | 一步撤回；或取消重来 |
| 录制中改了曲线 / 叠加开关 | 反解失真 | 整个模式冻结 |
| 崩在预览中 | `peace.txt` 停在建议 | 既有已知限制：`.peace` 未写，重开即恢复 |

## 9. 测试计划

自测（`tests/PeaceWpf.Core.SelfTest`，目标 +35 项）：

- 记录器：静音帧不计、取样节奏、已知正弦落对频带、同一批帧算两次结果逐位相同。
- 分析器：平直输入 → 九条全 0；单频突出 → 只削该带、邻带不动；强度 0 → 全 0；
  强度 1 → 等于夹取值；齿音永不为正；低频不超 +6；
  已知 EQ 下 `OthersGainAt` 扣得对（`source` 回到平）。
- 估计函数：剔除 0% 等于全量均值；剔除 30% 后单帧爆音进不了结果；时间范围裁掉一段，结果跟着变；
  削波帧永远不计；中位谱逐带独立，不做跨带耦合。
- 逐带剔除：w=1 的带留下的帧数比 w=0 的多；两遍结果稳定；`X_b` 夹在 0–30%；
  安静剔除仍是帧级——改成逐带后各带均值被抬高的幅度不同，形状会变形（自测里锁住这一点）。
- 事件与拟合：80 Hz 的 400 ms 轰鸣不算爆音、80 Hz 的 150 ms 尖峰算；10 kHz 的 150 ms 算；
  只丢被判的那条带，邻带不受影响；同一形状出现 3 次的短事件被保留；
  峰位偏移时频率跟着挪、Q 随半高宽变化；
  责任区间外的缺陷不会把某一条拽出 Covers；峰 < 1.5 dB 时保持默认频率和 Q。
- 强度映射：0% 时剔除 2%、安静 0%、增益 0；100% 时 20% / 40% / 1.0；60% 落在剔除 8% 附近。
- 方向表：8×9 完整、无越界、约束生效；目标值必须等于来源换算值。
- 状态机：倒数结束才进录制；暂停、继续都不丢数据；取消清空；应用后清空并退模式；有效帧 < 30 不出建议；
  应用后置脏且撤回 +1；对比不置脏、不改撤回栈；
  模式中 `PreviewIncludeBass` 跟随叠加开关，而不是 `PreviewOverlayBass`（后者在编辑左右时固定为 false）。

手测：

1. 进模式 → 手动那排消失，出现方向 / 强度 / 开始录制 / 取消。
2. 开始录制 → 声音立刻变"无风味"，倒数 → 停 1 秒 → 按钮变「暂停录制」。
3. 录制中九条曲线逐步成形；拖方向或强度只改图、不改声。
4. 暂停 → 对比 / 应用 / 取消出现，声音切成建议。
5. 继续录制 → 立刻接着录、没有倒数；曲线接着长。
6. 对比两下 → 声音在校准链和建议之间来回；Ctrl+Z 无反应、保存按钮不出现。
7. 应用 → 回手动控件、保存按钮出现、Ctrl+Z 能退回。
8. 保存 → 重开风味还在；不保存退出 → 没留下。
9. 取消 → 声音回进入前、数据清空，之前的未保存改动还在。

实现时改掉的两处设计（测试逼出来的，已同步正文）：

1. 拟合原来只取 Δ 的最大正值，等于只能加不能减。改成按绝对值找峰，削和抬都管。
2. 「反复出现当内容」原来只豁免瞬态那一关，随后又被离群剔除扔掉，等于白判。现在豁免同时穿透两关。

自测：496 项全过，构建 0 警告 0 错误。还没做的：P4 按耳朵校四个方向的目标值，
以及 T(f) 的指数 0.4 和「重复 ≥3 次」这两个数——它们现在只是估计，必须用真实对局素材校。

补充（同日晚）：竞技定位按「脚步优先」重调——脚步 +4 → +7、爆炸 −4 → −7、枪声 +3 → +4、齿音 −1 → −2，
男声 / 女声回到 0（它们不该抢脚步的位置）；脚步增益上限提到 +8。图上给自动风味加了只读控制点和读数标签
（类型 · 频率 · 增益 · Q），手柄不能拖。

关于参考资料：当晚搜索接口不可用，几个猜的厂商页面也拿不到正文，所以这组数字不是抄来的曲线，
是按公开的声学常识推的——脚步主能量在 1.5–4 kHz、枪口爆音和爆炸的能量堆在 150–300 Hz 会掩盖它。
必须当作待校初值。

再补（峰位避让）：拟合时把每条的责任区间往内收 12%（最多 1/4 倍频程），不让两边的峰正好落在同一个中点上。
收完仍然相邻不到 1/3 倍频程，就只留「更符合」的那条：增益差别超过 0.5 dB 时留该改得多的，
差别不大时留离自己默认中心更近的；另一条增益归零、频率和 Q 不动（`AutoFlavorAnalyzer.SeparatePeaks`）。
这样正常情况下不需要分摊上限，分摊那一步退成兜底。

再补（重叠兜底）：分开之后带宽仍可能交叠，两条各自没超上限、叠起来可能推过 0 dBFS 削波。
所以建议出完还走一步 `LimitOverlap`：相邻两条同时提升时按合成峰值超出的比例一起收回，两条都在削时不动。
手动拖动不受影响——那是用户自己看着曲线做的决定。

再补（九条版，同日晚）：表从八条改成九条，按频率升序为
爆炸 80 / 余震 220 / 男声 700 / 女声 1800 / 脚步 2500 / 枪声 4500 / 齿音 7000 / 空间 12000 / 尖啸 17000。
前八条沿用彩虹色，尖啸用白色（它只该削，颜色也跟别人区分）。方向表、全局上限、中频参考点都跟着改成九项。
旧存档里 `mech` 这个 key 会被忽略，`gun` 保留但默认频率与覆盖范围变了。

图标与气泡：自动风味时每条都画只读控制点、图标和四行气泡（类型 / 频率 / 强度 / Q）。
气泡抬的在上、削的在下，按序号从上往下贪心避让，撞到底边就翻到上面；
外框用曲线自己的颜色，虚线连回控制点；图标画到气泡的反侧，免得被挡住。
